# STUB INSTRUCTION — How to compress a SKILL.md into a lazy-loaded stub

> **Read this before compressing any skill.** This is the canonical instruction.
> Any LLM (Claude, GPT, Gemini, local models) follows it the same way.

## Why we compress

Each SKILL.md loaded into context costs tokens. A skill you don't use this
session is dead weight. Lazy-loading replaces the full SKILL.md with a tiny
**stub** — the full content is preserved in a vault backup, and loaded on demand
only when the skill is actually invoked.

Goal: **cut context cost by ~80% without losing the ability to discover or invoke
any skill.**

## What is a stub

A stub is a SKILL.md that:

1. Keeps the **same `name`** in frontmatter (so the callable ID is unchanged)
2. Has a **short description** that lets the model decide *whether* this skill
   is relevant — without reading the full content
3. Points to the **vault backup** where the full content lives
4. Tells the model **how to load** the full content (via Read tool)

## What must survive in the stub

When you compress, these must remain intact in the stub's frontmatter or body:

- **`name`** — identical to the original (required for routing)
- **One-line essence** — what this skill does, in a sentence
- **Trigger signals** — when the model should reach for this skill
  (keywords, situations, file types — whatever the original uses)
- **Vault pointer** — the absolute path to the backup
- **Load instruction** — `Read("<vault-path>")` so the model knows how to expand

## What to throw away

Everything else can move to the vault and out of the stub:

- Detailed methodology and theory
- Worked examples
- Long prose explanations
- Code samples that aren't triggers
- Section-by-section walkthroughs

## The compression act is judgment, not a formula

You are not truncating to N characters. You are **distilling**:

- A debugging skill's stub should make "tests failing / build broken / unexpected
  behavior" obviously point to it
- A code-review skill's stub should surface "before merge / quality / correctness"
- A git-workflow skill's stub should trigger on "commit / branch / rebase / conflict"

Read the original, understand *when a model would want this skill*, and encode
exactly that into the stub description. Cut everything that isn't routing signal.

## Anatomy of a good stub

```markdown
---
name: debugging-and-error-recovery
description: "[lazy] Systematic root-cause debugging: reproduce, isolate, hypothesis, fix, verify. Use when tests fail, builds break, or behavior is unexpected. Vault: ~/.claude/lazy-skills/backups/.../SKILL.md"
---

<!-- stub generated by lazy-skill-loader at 2026-08-06T12:00:00.000Z -->
<!-- full content: ~/.claude/lazy-skills/backups/.../debugging-and-error-recovery/SKILL.md -->
<!-- use Read tool to load full instructions -->

# debugging-and-error-recovery (stub)

Full SKILL.md content has been moved to the lazy-skills vault to save context tokens.
Load it with:

​```
Read("C:/Users/<user>/.claude/lazy-skills/backups/.../debugging-and-error-recovery/SKILL.md")
​```
```

The description line is the only thing the model sees in the index. Make it count:
- `[lazy]` marker — flags this as a stub (so we don't re-compress it)
- Essence — what it does
- Triggers — when to use it
- Vault pointer — where the full content is

## Procedure for one skill

1. **Read** the original SKILL.md
2. **Backup** the original to the vault (do not modify the backup)
3. **Distill** the description per the rules above
4. **Write** the stub back to the original SKILL.md location
5. **Record** the entry in the vault registry (source_path, vault_path, hashes)

## After compressing all skills — rebuild the registry

The session-start hook reads a registry to build the model-facing index.
Rebuild it so the stubs' descriptions show up:

```bash
node bin/update-registry.js
```

This scans the vault + existing registry and writes a fresh
`registry/skills-registry.json` local to this machine. **Never commit the
registry** — it is per-user, generated from whatever skills they have installed.
