# Skill Patching Specification

This document defines what lazy-skill-loader patches, how patches are applied, what can go wrong, and how to recover. It is the contract that `lazy-bootstrap` (CLI) and `hooks/session-start.js` (drift detection) must satisfy.

## 1. Goal

Reduce per-request context overhead from ~9–12K tokens (full skill discovery) to ~2K (L1 index + stub descriptions). Preserve all callable IDs so existing `Skill('<plugin>:<name>')` invocations keep working.

## 2. What we patch

A `SKILL.md` file qualifies for patching when:

- It lives under `~/.claude/skills/<name>/SKILL.md` (custom skills), **or**
- It lives under `~/.claude/plugins/cache/<owner>/<plugin>/<version>/skills/<dir>/SKILL.md` (plugin skills).
- It has valid YAML frontmatter with both `name` and `description` fields.

Files outside these locations are ignored.

## 3. What we do NOT patch

| Case | Reason |
|---|---|
| `~/.claude/skills/lazy-skill-loader/SKILL.md` | Self — patching would break the loader. Hardcoded in `SELF_NAME`. |
| Files without frontmatter or `name` field | Cannot render a valid stub. Reported as error. |
| Files that are already stubs but not in registry | Means external patcher or registry wipe. Reported as error; manual restore required. |
| Any file outside `~/.claude/skills/` or `~/.claude/plugins/cache/` | Out of scope. |

## 4. Patch contract

For each patched skill, the loader:

1. Reads original `SKILL.md` content (call it `original`).
2. Computes `original_hash = sha256(original)`.
3. Backs up `original` to vault: `~/.claude/lazy-skills/backups/<custom\|plugins>/<...>/SKILL.md`. The backup is byte-exact.
4. Renders a stub and writes it to the original path.
5. Appends an entry to `~/.claude/lazy-skills/vault-registry.json` with `original_hash`, `stub_hash`, `source_path`, `vault_path`, and metadata.

### Stub format

```markdown
---
name: <original-name-unchanged>
description: "[lazy] <short hint ~80 chars>. Vault: ~/.claude/lazy-skills/backups/<path>"
---
<!-- stub generated by lazy-skill-loader at <ISO date> -->
<!-- full content: ~/.claude/lazy-skills/backups/<path>/SKILL.md -->
<!-- use Read tool to load full instructions -->

# <name> (stub)

Full SKILL.md content has been moved to the lazy-skills vault to save context tokens.
Load it with:

Read("<absolute vault path>")
```

Invariants:

- `name` is **byte-identical** to the original — preserves callable IDs and plugin namespace.
- `description` starts with `[lazy] ` marker (so `isStub()` can detect our stubs) and ends with `Vault: <path>` pointer.
- Body is fixed template, ~30 tokens total.

### Backup layout

```
~/.claude/lazy-skills/
├── vault-registry.json
└── backups/
    ├── custom/
    │   └── audit-pattern/SKILL.md
    └── plugins/
        ├── agent-skills/1.0.0/test-driven-development/SKILL.md
        └── superpowers/5.1.0/test-driven-development/SKILL.md
```

Custom skills are keyed by `original_name`. Plugin skills are keyed by `<plugin>/<version>/<skill_dir>` — this supports multiple versions of the same plugin and plugins from different owners sharing a skill name.

## 5. Idempotency

A second `--apply` is a no-op when nothing has changed. Concretely, for each candidate:

1. If registry has an entry with same `source_path` and its `stub_hash` matches `sha256(current file content)` → **skip** (count as `skipped`).
2. If the file is already a stub but no registry entry exists → **error** (someone else patched it or registry was wiped).
3. Otherwise → **apply** (backup + patch).

The deduplication key is `source_path` (not `stub_id`), so two versions of the same plugin skill coexist as separate entries.

## 6. Drift detection

Plugin updates (e.g. `git pull` in marketplace) can overwrite our stubs with new original content. After such an event, the on-disk `SKILL.md` no longer matches the recorded `stub_hash`.

`hooks/session-start.js` runs drift detection on every session start:

1. Reads `~/.claude/lazy-skills/vault-registry.json`.
2. For each entry: compute `sha256(current source_path content)` and compare to `entry.stub_hash`.
3. If any differ, emit a warning listing drifted `stub_id`s and instruct the user to run `lazy-bootstrap --sync`.

Cost: SHA-256 of each stub file (~60 bytes each). No full SKILL.md reads. ~1ms per entry for a typical registry.

### `--sync`

`--sync` re-applies stubs only to drifted entries. The vault backup is preserved (we trust it's the original). After `--sync`, drift is cleared.

`--sync --force` re-applies stubs to **all** entries (use only when registry state is suspect).

## 7. Restore contract

`--restore [glob]` restores originals from vault backups:

- Without glob: restores all entries, then wipes the registry.
- With glob (e.g. `agent-skills:*`): restores matching entries; non-matching entries stay in registry.
- With `--keep-registry` (programmatic API): restore files but leave registry intact.

Restore writes are **byte-exact** copies of the backup. If a backup is missing, the entry is reported as error and kept in registry for manual resolution.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Claude Code rejects stub frontmatter | Smoke test on one plugin skill before bulk apply. If rejected, fall back to L1-only mode (no patching). |
| Plugin update overwrites stub | Drift detection warns; `--sync` re-applies. Worst case: full description returns to context (back to ~9K, no crash). |
| Plugin changes directory layout | `source_path` stored absolute; restore warns on missing path. |
| User deletes `vault-registry.json` | Restore can work directly from `backups/` tree if needed; CLI can regen registry from backup paths. |
| Multiple plugin versions installed | Backups keyed by `<plugin>/<version>/<skill_dir>`; all coexist. |
| Windows path separator issues | All paths in registry stored with forward slashes; backslash normalization on read. |
| New skills added after bootstrap | Not in registry → not stubbed → still loaded normally. No data loss; user can run `--apply` again. |

## 9. CLI commands

```
lazy-bootstrap --apply [--no-custom] [--no-plugins] [--plugin NAME]
    Default. Backup + patch all qualifying skills.
    --plugin NAME restricts the scan to a single plugin (e.g. agent-skills).

lazy-bootstrap --check
    Report drift only. No filesystem changes. Exit 1 if drifted.

lazy-bootstrap --sync [--force]
    Re-apply stubs to drifted entries. Use --force for all.

lazy-bootstrap --restore [glob]
    Restore originals. Optional glob filters by stub_id (e.g. "agent-skills:*").

lazy-bootstrap --list
    Show all vault entries with source and version metadata.
```

## 10. Verification (post-bootstrap)

After running `--apply`, verify:

1. `npm test` is green — all unit + integration tests pass.
2. `lazy-bootstrap --list` shows expected entries (~count of installed skills).
3. `lazy-bootstrap --check` returns exit 0 (no drift).
4. New Claude Code session starts without error.
5. `available-skills` system reminder contains stub descriptions (with `[lazy]` marker).
6. Calling `Skill('<plugin>:<name>')` still resolves.
7. `Read("~/.claude/lazy-skills/backups/<path>/SKILL.md")` returns full original content.

## 11. Out of scope

The loader does **not**:

- Disable plugins via `enabledPlugins` — namespace must remain active.
- Change the `name` field in stub frontmatter — callable IDs stay the same.
- Patch `lazy-skill-loader` itself — protected by `SELF_NAME`.
- Read vault content in `session-start.js` — that would defeat the savings.
- Run `--apply` automatically at install time — only explicit user invocation.
- Add `lazy-bootstrap` to `npm install` postinstall hooks — risky.
